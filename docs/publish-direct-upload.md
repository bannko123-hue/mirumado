## 1. いちばん大事な注意 — **後から GitHub 連携に「切り替える」ことはできません**

**これは知らずに進むと後戻りが面倒になる点なので、最初に書きます。**

Cloudflare の公式ドキュメントに、はっきりこう書かれています。

> "If you choose Direct Upload, you cannot switch to Git integration later."
> （直接アップロードを選んだ場合、後から Git 連携に切り替えることはできません）
>
> "You will have to create a new project with Git integration to use automatic deployments."
> （自動デプロイを使うには、Git 連携で**新しいプロジェクトを作り直す**必要があります）
>
> — 出典: <https://developers.cloudflare.com/pages/get-started/direct-upload/>（2026-09-24 確認）

### これが何を意味するか

`launch-checklist.md` は「GitHub が繋がったら Pages を Git 連携に切り替える」という前提で書かれていましたが、**その「切り替え」という操作は存在しません。** 実際にやることになるのは次のどちらかです。

| | やり方 | 起きること |
|---|---|---|
| **X** | 直接アップロードの `mirumado` プロジェクトを**削除**してから、同じ名前 `mirumado` で Git 連携プロジェクトを作り直す | URL は `mirumado.pages.dev` のまま維持できる。ただし**削除から作り直しまでの数分間、サイトが見られなくなる** |
| **Y** | 直接アップロードの `mirumado` を残したまま、別名（例 `mirumado-git`）で Git 連携プロジェクトを作る | URL が `mirumado-git.pages.dev` に変わる。**`site.json` の `baseUrl` の直し・Search Console の登録し直し・ASP に登録した URL の変更**が全部ついてくる（→ `handover.md` §4-4） |

**X のほうが被害は小さい**ですが、**「プロジェクトを削除すると `mirumado` という名前がすぐに解放されて、同じ名前で作り直せるか」は公式ドキュメントに記載を見つけられませんでした（未確認）。** 理屈のうえでは解放されるはずですが、確認できていないので断定しません。**X をやるときは、削除する前に「本当にやるか」を一度考えてください。**

### それでも今 zip で公開すべきか

**公開を待つデメリットのほうが大きい、というのが現時点の見立てです。** 理由:

- **サイトが公開されていないと ASP の個別提携申請に進めない**（`docs/afb-partner-plan.md` ⓪）。afb は媒体審査を 9/20 に通過済みで、**止まっているのは公開だけ**です。
- Search Console の登録（#13）も公開が前提。
- 記事22本はもう出来ています。**寝かせている間に価格改定（10/01）が来ると、公開前から情報が古くなります**（`docs/price-change-2026-10-01.md`）。

**逆に、GitHub の接続が「あと数日で直りそう」なら、待ってから #5 → #6 に進むほうが素直です。** 作り直しの手間が丸ごと要りません。**どちらを選ぶかは本人判断です。**

## 2. 準備するもの

**アップロードする zip は作成済みです。**

| | |
|---|---|
| **ファイル** | `/mnt/project-files/mirumado-site-2026-09-24.zip` |
| **サイズ** | 268 KiB（274,526 バイト） |
| **中身** | 38ファイル（HTML 32ページ＋ `assets/` 2ファイル＋ `sitemap.xml` `feed.xml` `robots.txt` `search-index.json`）／展開後 1.06 MiB |
| **構造** | **`index.html` が zip の直下にあります**（`dist/` フォルダは挟まっていません）。確認済み |

> **なぜ「直下」が大事か**: zip の中が `dist/index.html` になっていると、Cloudflare は `dist` という名前のサブフォルダごと公開してしまい、トップページが `mirumado.pages.dev/dist/` になります。**この zip はその状態になっていないことを `unzip -l` で確認済みです。**

**zip を自分で作り直す場合**（記事を直したあとなど）は、必ず `dist` の**中に入ってから**固めてください。

```bash
cd <プロジェクトのディレクトリ>
node build.mjs                                  # 本番ビルド（--drafts は付けない）
node build.mjs --check                          # エラー0 を確認（警告57件は正常）
cd dist
rm -f ../../mirumado-site.zip
zip -r -q ../../mirumado-site.zip . -x '.*'     # 「.」= dist の中身だけを固める
unzip -l ../../mirumado-site.zip | head         # index.html が直下にあることを目視確認
```

**`zip -r mirumado-site.zip dist` としないこと。** これをやると `dist/` が1階層挟まります。

## 3. 公開の手順

### 手順 1 — Cloudflare のアカウントを作る（10分。既にあれば飛ばす）

1. <https://dash.cloudflare.com/sign-up> でアカウントを作る。
2. 確認メールのリンクを踏んで有効化する。
3. **カード入力を求められたら、そこで止まって確認してください。** Pages の無料プランはカード登録なしで使えるはずですが、求められた場合は `launch-checklist.md` #2 の判断ポイントに戻ります。

**ドメインを Cloudflare に追加する（Add a site）操作は不要です。** 今回使うのは Pages だけで、DNS は触りません。

### 手順 2 — 直接アップロードでプロジェクトを作る（5分）

公式ドキュメントの手順は次のとおりです（引用元は §0 の表）。

1. **"In the Cloudflare dashboard, go to the Workers & Pages page."**
   ダッシュボード左のメニューから **Workers & Pages** を開く。
2. **"Select Create application > Get started > Drag and drop your files."**
   **Create application**（アプリケーションを作成）→ **Get started**（開始する）→ **Drag and drop your files**（ファイルをドラッグ＆ドロップ）を選ぶ。
   - 画面に **Pages** と **Workers** のタブが出る場合は **Pages** のほうを選んでから進みます。
3. **"Enter your project name in the provided field and drag and drop your assets."**
   **プロジェクト名の入力欄に `mirumado` と入れる。**
4. 同じ画面に zip をドラッグ＆ドロップする。
5. **"Select Deploy site."** — **Deploy site**（サイトをデプロイ）を押す。

#### プロジェクト名について（**ここがいちばん間違えやすい**）

**必ず `mirumado`（半角小文字のみ）** と入力してください。**この文字列がそのまま `mirumado.pages.dev` の `mirumado` になります。**

- `mirumado-site` や `Mirumado` や `mirumado2` にすると URL が変わり、`content/site.json` の `baseUrl`（`https://mirumado.pages.dev`）と食い違います。**食い違うと canonical・sitemap・robots.txt が全部まちがったドメインを指したまま公開されます。**
- **`mirumado` が他のユーザーに先に取られていて弾かれる可能性があります。** `.pages.dev` のサブドメインは全 Cloudflare ユーザー共通の名前空間です。
  弾かれた場合は、**別名を決めて → `content/site.json` の `baseUrl` をその名前に直し → `node build.mjs` → `node build.mjs --check` を通し直し → zip を作り直してからアップロード**してください（`handover.md` §4-2）。**古い zip のまま別名で公開しないこと。**

#### zip について

**zip のままアップロードできます。** 公式ドキュメントに次の記載があります。

> "Drag and drop: A zip file or single folder of assets."
> — 出典: <https://developers.cloudflare.com/pages/get-started/direct-upload/>（2026-09-24 確認）

zip を解凍してフォルダごとドラッグしても構いません。その場合は **`dist` フォルダ自体ではなく、`dist` の中身が入ったフォルダ**を渡すことになる点に注意してください（`dist` を渡すと1階層挟まります）。

### 手順 3 — 公開できたことを確認する（5分）

デプロイが終わると URL が表示されます。次の4つをブラウザで開いて確かめてください。

- `https://mirumado.pages.dev/` — **トップページが出る**（`/dist/` が URL に挟まっていないこと）
- `https://mirumado.pages.dev/sitemap.xml` — `<loc>` が `https://mirumado.pages.dev/...` になっている
- `https://mirumado.pages.dev/robots.txt` — `Sitemap:` 行が同じドメインを指している
- `https://mirumado.pages.dev/soccer/` — カテゴリページが出る（サブディレクトリが正しく展開されている証拠）

さらに、トップの HTML ソースを表示して **`<link rel="canonical" href="https://mirumado.pages.dev/">`** になっていることを確認します。

**URL がプロジェクト名どおりになっているか**も必ず見てください。`site.json` の `baseUrl` と1文字でも違っていたら、§3 手順2 の「弾かれた場合」に従って直します。

## 4. 公開した直後にやること — `【要記入】` の残り1項目を埋める

> **本来は公開の前に埋めるのが望ましい**（`launch-checklist.md` の「やる順 1」）。**先に公開してしまった場合は、最優先でここをやってください。** 連絡先が `【要記入】` のまま出ているサイトは、ASP の審査で体裁を疑われる理由になります（#15）。

### 出ている場所（`dist/` を実測。2026-09-26）

**本番HTMLに出るのは2箇所**で、**どちらも同じ1項目（`contactEmail`）から出ています。**

| # | ページ | 見出し | 画面に出ている文言 |
|---|---|---|---|
| 1 | `/about/` | **「運営者」** | `連絡先: 【要記入】` |
| 2 | `/policy/` | **「運営者情報」** | `連絡先: 【要記入】` |

### 直す場所（**表示2箇所に対して、直すのは1箇所**）

**`dist/` の HTML を直接いじらないでください。** `dist/` はビルドのたびに作り直されるので消えます。**直すのは次の元ファイルです。**

| 直す場所 | 変数・キー | どの表示になるか |
|---|---|---|
| `content/site.json` の `contactEmail` | `"contactEmail": "【要記入】"` | **上の表 #1 と #2 の両方**（1箇所直すと2箇所とも埋まる） |

**2026-09-26 に処理済みのもの（本人の手は要りません）**

- **運営者名**（`/about/` と `/policy/`）: 暫定で **「みるまど編集部」**。`/policy/` の当該項目は「運営者名（ハンドルネーム可）」なので、ハンドル名として成立します。**本名や別の屋号にしたいときは、`build.mjs` の `buildAbout()` と `buildPolicy()` の `ownerName` を、必ず同じ表記に差し替えてください**（`/about/` と `/policy/` で名前が違うと不審に見えます）。
- **所在地**（`/policy/`）: **住所は捏造せず、空の `【要記入】` も出しません。** 住所の行そのものを出さず、「所在地については、法令に基づく請求があった場合に遅滞なく開示します。」の一文を出す形にしました。**`build.mjs` の `buildPolicy()` の `ownerAddress` に住所を入れれば、これまでどおり「所在地」の行が表示に戻ります。**
  - **これは法的助言ではなく、個人運営のアフィリエイトサイトでよく取られている形に合わせた暫定措置です。「法律上不要」と判断したわけではありません。** **ASP や取引先から住所の記載を求められたら `ownerAddress` に入れれば表示が戻ります。** 特商法表記が要るかどうかの確認は `launch-checklist.md` #15 に残っています。

**注意点**

- **メールアドレスは本人の個人情報なので、この文書でも埋めていません。捏造もしません。**

### 埋めたあと（**ここを忘れると公開サイトは古いまま**）

**直接アップロードは自動デプロイではありません。ファイルを直しても、アップロードし直すまで公開サイトは変わりません。**

```bash
cd <プロジェクトのディレクトリ>
node build.mjs
node build.mjs --check                 # エラー0 を確認
grep -rc '【要記入】' dist/ | grep -v ':0$'   # 何も出なければ全部埋まった
cd dist
zip -r -q ../../mirumado-site.zip . -x '.*'
```

そのうえで **§5 の「2回目以降の更新」** の手順でアップロードし直します。

## 5. 2回目以降の更新のしかた

記事を直したときも価格改定（10/01）のときも、**更新は必ず本人の手作業になります。** 方法は2通りです。

### (a) 同じ zip 手順を繰り返す（当面これ）

1. `node build.mjs` → `node build.mjs --check`（エラー0）
2. `cd dist && zip -r -q ../../mirumado-site.zip . -x '.*'`
3. ダッシュボード → **Workers & Pages** → プロジェクト `mirumado` を開く
4. デプロイを作成する導線（**Create deployment** 系）から、新しい zip をアップロードする
5. 反映を確認する

**1回あたり5分程度。** ただし **記事を直すたびに毎回これが要ります。** ここが zip 運用のいちばんの弱点です。`docs/daily-operation.md` の「朝の執筆・公開」を毎日回すなら、**この手間が毎日乗ります。**

> **手順 3〜4 のダッシュボード上の正確な導線（ボタン名）は未確認です。** 公式ドキュメントで確認できたのは**新規プロジェクト作成時**のドラッグ＆ドロップ手順で、**既存プロジェクトへの2回目以降のアップロード導線の画面名は、この環境から取得したページには明示がありませんでした。** プロジェクトの画面で「デプロイ」「アップロード」に当たる導線を探してください。

### (b) GitHub が繋がったら Git 連携に移す（**本命はこちら**）

**push するだけで自動デプロイされる状態が最終形です。** 記事を直して `git push` すれば Cloudflare が勝手にビルドして公開してくれるので、**§5(a) の手作業が丸ごと消えます。** `docs/daily-operation.md` の運用を続けるなら、**ここに行き着かないと毎日の負担が減りません。**

**ただし §1 のとおり「切り替え」はできません。** 実際の手順は:

1. `launch-checklist.md` **#5** のとおり GitHub にリポジトリを作って push する
2. **直接アップロードの `mirumado` プロジェクトを削除する**（§1 の X。URL を維持するため）
3. `launch-checklist.md` **#6** のとおり、**Git 連携**で**同じ名前 `mirumado`** のプロジェクトを作る
   - Build command: `node build.mjs` ／ Build output directory: `dist` ／ `NODE_VERSION` = `20`
4. デプロイが緑になったら §3 手順3 の4点を確認する

**2 と 3 のあいだはサイトが見えなくなります。** ASP の審査中や、Search Console にサイトマップを送った直後は避けるのが無難です。

> **削除した名前がすぐ再利用できるかは未確認です**（§1）。**心配なら、先に (b) の 1 だけ済ませて GitHub 側を完成させておき、切り替えは腰を据えてできるタイミングでやる**のが安全です。

## 7. この方法を選んだときに「やらなくてよくなる」こと

`launch-checklist.md` との対応です。

| 項目 | zip 直接アップロードの場合 |
|---|---|
| **#5** GitHub にリポジトリを作って push | **不要**（ただし (b) に移るときに必要になる） |
| **#6** Pages に Git 接続して公開 | **この文書の §3 に置き換わる** |
| #4 Cloudflare アカウント作成 | **必要**（§3 手順1） |
| #9 `contactEmail` の穴埋め | **必要**（§4。**公開前が望ましい**。残りはこの1項目・表示2箇所だけ） |
| #12 再ビルド → 検証 → デプロイ | **必要**。ただし「デプロイ」は zip の再アップロード（§5(a)） |
| #13 Search Console | **必要**（公開後） |
| #17・#18 ASP | **必要**（公開後） |

**ローカルの git コミットは、GitHub を使わなくても続けてください。** 作業履歴が残っていれば、(b) に移るときに push するだけで済みます。
