### 2-3. メモの置き場所と書式

**置き場所: `notes/nightly/YYYY-MM-DD.md`**（新規ファイルだけを作る。`research/` の既存ファイルはこの時点では触らない）

```bash
mkdir -p notes/nightly
$EDITOR notes/nightly/$(date +%F).md
```

1件につき、次のブロックをそのままコピーして埋める。**「出典URL」と「原文の引用」が空のまま朝を迎えたネタは、朝の時点で捨てる。**

```markdown
## [S2] スカパー！プロ野球セットの月額が変わった

- 見つけた場所: https://www.skyperfectv.co.jp/info/
- 出典URL（数値が書いてあるページ）: https://www.skyperfectv.co.jp/plan/pack/basic/062
- 確認日: 2026-09-08
- 原文の引用: 「月額4,054円（税込）」
- 影響する既存記事: npb-live-streaming / baseball-streaming-services-hub / skyperfectv-baseball-review
- 仕分け: 既存更新
- 期限: なし（あれば「2026-10-01から」のように書く）
```

`[S1]`〜`[S5]` の記号を見出しに残しておくと、朝の仕分けが速い。

## 3. 仕分けのパート（夜の最後・10分）

### 3-1. 3つの行き先に振り分ける

| 拾った記号 | 行き先 | 判断の根拠 |
|---|---|---|
| **S1**（新しい固有名詞） | **新規記事** | その語で検索する人が今日から現れる。既存記事に段落を足しても、その語ではタイトルが当たらない |
| S1 だが、既存記事のタイトルで十分カバーできる | 既存更新 | 例:「Jリーグ第〇節の放送」→ `j-league-live-streaming` に節を足すだけでよい |
| **S2**（数値が変わった） | **既存更新（最優先）** | 古い数値を放置すると読者が損をする（§4-2） |
| **S3**（放映権が動いた） | 既存更新＋必要なら新規 | まず既存記事の該当箇所を直し、独占配信など大きい動きなら新規1本 |
| **S4**（期限が迫った） | 既存更新（日付を決めて予約） | `handover.md` §3 の期限表に載っているものは、その日に必ず直す |
| **S5**（仕様変更） | 既存更新 | 比較表の列が変わることが多い |
| X1〜X5 | **捨てる** | 迷ったら捨てる。翌日また出てくる |

### 3-2. 既存記事の `updated` を直す運用は、新規記事と同じくらい重要

このサイトは `build.mjs` の作りからして**鮮度が売り**になっている。`updated` を1日直すと、次のすべてが同時に動く（すべて `build.mjs` で確認済み）。

| 場所 | `updated` がどう効くか |
|---|---|
| トップページ「最近更新した記事」 | `updated` の降順で上位6本を並べる。直せばトップ面に出る |
| 記事ページの本文下 | 「**この記事の情報は 2026-09-08 時点の公式ページで確認したものです**」という一文が自動で入る |
| 記事ページのヘッダ | 「最終更新」として表示。`published` と同じ日なら「公開したばかり」バッジが出る |
| `sitemap.xml` | 記事の `<lastmod>` がそのまま `updated` |
| JSON-LD | `dateModified` が `updated` |
| `feed.xml` | `updated` の降順 |
| 記事下の「関連記事」 | `updated` の降順で並ぶ |

**だから守るルール**

1. **確認していない日に `updated` を上げない。** 上げると読者には「その日に公式で確認した」と表示される。確認していないのに上げるのは、読者への嘘になる。
2. **数値を1つでも直したら `updated` を必ず上げる。** 直したのに上げないと、古い日付のまま新しい数値が出て、`sources` の確認日と食い違う。
3. **本文を変えていなくても、公式ページを開き直して「数値が変わっていないこと」を確認した日は、`updated` を上げてよい。** そのとき `sources` の確認日も同じ日に揃える。これが「棚卸し」で、週1・月1でやる（§7）。
4. `updated` は `published` より前にできない（ビルドが止まる）。

### 3-3. 1日にやる本数の目安

- 新規記事: **1日1本まで。** 2本書くと事実確認が雑になる。
- 既存更新: 1日3本まで。数値の差し替えだけなら5本でも回る。
- 更新が5本を超えた日は、**その日は新規を書かない。**

## 4. 事実確認のルール（毎回・例外なし）

### 4-1. 4つのルール

1. **数値は公式ページで確認する。** 公式サイト・公式ヘルプセンター・公式ニュースリリースだけ。リーグの公式サイトに書かれた他社サービスの情報（例: Jリーグ公式に書かれたDAZNの配信範囲）は、**そのリーグ公式ページを出典として**使ってよい。
2. **確認したら `sources` に URL と確認日を書く。** `build.mjs` の `sources` には確認日を書く欄が無いので、**`note` に確認日を書く**か、本文に「2026年9月8日時点の公式ヘルプ記載」と書く。1つの数値に1つの出典を対応させる。
3. **確認できないものは書かない。** 「たぶん」「おそらく」「〜と思われる」を使わない。公式が日数を書いていないなら「〇日間」と書かない（TVerの見逃し配信がこれ）。書けなかった項目は `research/unverified.md` に足す候補としてメモに残す。
4. **まとめサイト・アフィリエイト記事・SNSは出典にしない。** ページの存在を知る手がかりに使うのはよいが、`sources` には入れない。

### 4-2. このルールを破ると何が起きるか

| 破り方 | 起きること |
|---|---|
| 古い月額をそのまま載せる | 読者がその金額のつもりで申し込み、**請求額が違う**。返品・キャンセルにつながる |
| 無料トライアルが無いのに「無料で試せる」と書く | 読者が無料のつもりで有料契約する。**苦情と解約**が発生し、広告主が成果を却下する |
| 公式に無い日数（「見逃しは7日間」など）を書く | 期限を過ぎて見られず、**読者が損をする**。修正しても信頼は戻らない |
| 却下条件（既存ユーザー除外・アプリ経由除外）を書かずに申し込ませる | 成果が却下されて報酬にならないうえ、**読者は条件を満たさないまま課金**される |
| これが積み上がる | 広告主から**提携を切られる**。ASP からも**アカウント停止**の対象になりうる。個人サイトはここで終わる |

**このサイトの資産は記事本数ではなく「書いてあることが本当だ」という一点しかない。** 1本の不正確な記事が、20本の正確な記事の価値を消す。

## 5. 朝のパート（執筆・60〜90分／更新は15〜25分）

### 5-1. まず記事ファイルを作る

```bash
# slug は plan.md の一覧から取る。半角英数字とハイフンのみ
$EDITOR content/articles/<slug>.md
```

書き上がるまでは先頭を `_` にしておくと本番ビルドから外れる（`_<slug>.md`）。公開する朝に `_` を外す。

```bash
mv content/articles/_j-league-live-streaming.md content/articles/j-league-live-streaming.md
```

### 5-2. フロントマターのひな型（全 role 共通・そのままコピー）

```markdown
---
title: 
description: 
category: サッカー
role: entry
target_keyword: 
search_intent: 
published: 2026-09-08
updated: 2026-09-08
sources:
  - label: 
    url: https://
    note: 2026-09-08 確認
ad_slots:
  - id: slot-hero
    program: 
    note: 
---
```

**フロントマターで踏みやすい罠（3つとも実測済み）**

| 罠 | 何が起きるか | 対処 |
|---|---|---|
| ~~`title` に半角スペース付きの `#` を入れる~~ | **2026-09-08 に修正済み。** 以前は `#` 以降がエラーも警告も無く消えていた（`title: Jリーグ 第1節 # 第2節の見方` → `<title>Jリーグ 第1節`）。現在は値の途中の `#` はコメントとみなさず、**全体がそのままタイトルになる** | 対処不要。`"` で囲んでも囲まなくてもよい |
| `sources` の2件目以降で `- ` を書き忘れる | 出典が1件に減り、あとで **`::source{2} は範囲外です`** という無関係に見えるエラーになる | `- label:` の `- ` を必ず付ける |
| `::ad{id=...}` を文中に書く | ビルドが止まる | 必ず行を独立させ、前後を空行で挟む |

### 5-3. role 別の見出しのひな型

`plan.md` の `role` に合わせて、下の型をそのまま本文に貼ってから中身を埋める。広告枠の位置は `ad-placement.md` と一致させること。

> **`::ad{...}` は、提携前でもひな型のまま本文に書いてよい**（2026-09-08 の `build.mjs` 改修による）。`ad_slots` に `html:` が入っていない枠は、**本番ビルドでは何も出力されない**ので、読者には何も見えない。未挿入の枠は `node build.mjs --check` の**警告**として列挙されるだけで、エラーにはならない。提携が通ったら該当する `ad_slots` に `html:` を1行足す。詳細は `ad-placement.md` §2-4・§3-2。

#### entry（入口記事・11本）— 「今夜これを見たい」に最短で答える

読者は**すでに見たい試合が決まっている**。結論を最初の3行に置く。

```markdown
（リード文2〜3行。「この記事は◯◯を見る方法をまとめたものです」ではなく、いきなり結論の前置き）

## 結論：{対象}を見るなら{サービス名}
```

## 6. 公開のパート（10分）

### 6-1. コマンド列（この順で・省略しない）

```bash
# 1) 下書き込みで一度ビルドして、手元で見る
node build.mjs --drafts --check
node serve.mjs                 # http://127.0.0.1:4000/ を開いて記事を目で確認。Ctrl+C で止める

# 2) 本番ビルド（_ 始まりは除外される）＋検証
node build.mjs --check

# 3) 警告がゼロか確認する（警告はビルドを止めないので、自分で見る）
node build.mjs --check 2>&1 | tee /tmp/miru-build.log
grep -c '\[警告\]' /tmp/miru-build.log     # 「0」が出ればよい

# 4) 終了コードを確認する（0 でなければ検証NG）
node build.mjs --check > /dev/null; echo "exit=$?"     # exit=0 を確認

# 5) デプロイ（Cloudflare Pages に GitHub 連携している場合）
git add content/articles/<slug>.md
git commit -m "add: <slug>"
git push                                    # push で自動ビルド・自動公開
```

**公開してよい条件は次の3つが全部そろったとき。**

1. `node build.mjs --check` が `検証: 問題は見つかりませんでした。` を出す
2. `[警告]` が 0 件
3. サマリの「広告枠 N 箇所」が、その日に置いたはずの枠数と一致する

ビルド完了時のサマリはこう出る。数字を毎回見る。

```
ビルド完了: dist
  記事 2 本（うち下書き/サンプル 2 本）
  広告枠 4 箇所
  出典リンク 3 本
  HTML 12 ページ / アセット 2 ファイル
  FAQ 構造化データつきの記事 1 本 / 本文中の外部リンク 2 本
```

- 「出典リンク」が思ったより少なければ、`sources` の `- ` 書き忘れを疑う。
- 「FAQ 構造化データつきの記事」が増えていなければ、`## よくある質問` の見出しの書き方を疑う。

### 6-2. エラーが出たときの読み方

`build.mjs` はエラーを1件出して即座に止まる。**必ず「ファイル名: 内容」の形で出る**ので、そのファイルだけ見ればよい。

```
ビルドを中止しました:
  content/articles/xxx.md: （ここに理由）
```

#### ビルドが止まるエラー（実際に出るメッセージと直し方）

| 出るメッセージ | 原因 | 直し方 |
|---|---|---|
| `フロントマターの必須項目が足りません → description` | 8つの必須項目のどれかが無い／空 | `title` `description` `category` `role` `target_keyword` `search_intent` `published` `updated` を全部書く |
| `role は entry / hub / conversion のいずれかにしてください（現在の値: "entrypoint"）` | `role` の綴り違い | `plan.md` の role をそのまま写す |
| `category "バスケ" は content/site.json に定義されていません。 使えるカテゴリ: サッカー / 野球 / 格闘技・ボクシング / エンタメ・音楽 / サービス比較` | カテゴリ名が5つ以外 | 5つのどれかに寄せる。増やしたいなら `site.json` の改修が要る（サイト担当へ） |
| `フロントマターの published は YYYY-MM-DD 形式で書いてください（現在の値: "2026/09/01"）` | 日付がスラッシュ区切り | `2026-09-01` に直す |
| `updated (2026-08-01) が published (2026-09-01) より前になっています` | 更新日が公開日より前 | `updated` を `published` 以降にする |
| `1 行目が "---" ではありません。記事は "---" で囲んだフロントマターから始めてください` | 先頭に空行やBOM、`---` の打ち間違い | ファイルの1行目を `---` だけにする |
| `フロントマターを閉じる "---" が見つかりません` | 閉じの `---` が無い | フロントマターの末尾に `---` を足す |
| `フロントマター N 行目が "キー: 値" の形になっていません` | コロンの抜け、全角コロン | 半角の `: ` に直す |
| `フロントマター "sources" 配下の N 行目は "- " で始めてください` | リストのハイフン抜け | `- label:` の形にする |
| `sources[1] には label と url の両方が必要です` | どちらかが空 | 両方書く |
| `sources[1] の url は http(s):// から始まる URL にしてください（現在の値: "example.com/plans"）` | スキーム無し | `https://` を付ける |
| `::source{9} は範囲外です（sources は 2 件。1〜2 を指定してください）` | 出典番号の指し間違い、または `sources` の `- ` 書き忘れで件数が減っている | まず `sources` の件数を数える。件数が想定より少なければ `- ` の書き忘れ |
| `::source{1} が使われていますが、フロントマターに sources がありません` | `sources` を書いていない | `sources` を足す |
| `::ad{...} は必ず行を独立させて書いてください（前後を空行で挟む）。文中には置けません。` | `::ad{}` を文章の中に書いた | 独立した行にし、前後に空行を入れる |
| `::ad{id=slot-top} に対応する ad_slots が見つかりません。（現在定義済み: slot-hero, slot-compare, slot-footer）` | 本文の id とフロントマターの id が食い違う | どちらかを合わせる。使う id は `slot-hero` / `slot-mid` / `slot-compare` / `slot-footer` の4種 |
| `ad_slots の id "slot-hero" が重複しています` | 同じ id を2回定義した | 1つにする。同じ位置に2件並べたいなら `ad-placement.md` の方針に従う |
| `スラッグ "sample-1" が重複しています（content/articles/_sample-1.md と content/articles/sample-1.md）` | `_` 付きと `_` 無しが両方ある | 片方を消す。公開に切り替えたら `_` 付きは残さない |
| `本文が空です` | フロントマターだけのファイル | 本文を書く |
| `content/site.json が JSON として読めません` | site.json を壊した | `git checkout content/site.json` で戻す。ここは基本触らない |

#### ビルドは通るが直すべき警告

```
  [警告] content/articles/xxx.md: ad_slots に "slot-footer" がありますが、本文に ::ad{id=slot-footer} がありません
```

→ フロントマターに枠を定義したのに本文に置き忘れている。**本文に `::ad{id=slot-footer}` を足すか、フロントマターから枠を削る。** 放置すると広告枠の数が合わなくなり、`ad-placement.md` の対応表とずれる。

#### `--check` で出る検証エラー（ビルドは成功、終了コードが 1 になる）

```
検証で問題が見つかりました:
  - soccer/xxx/index.html: 内部リンク切れ → /soccer/nothing-here/
```

| 出るメッセージ | 原因 | 直し方 |
|---|---|---|
| `内部リンク切れ → /soccer/xxx/` | 本文の内部リンク先の記事がまだ無い／slug 違い | リンク先の slug を確認する。まだ書いていない記事へのリンクは**書かない**（先に書いてから貼る） |
| `ページ内アンカーの飛び先がありません → #source-3` | `::source{3}` の飛び先が無い | `sources` の件数を確認する |
| `JSON-LD が不正な JSON です` | フロントマターの値に壊れた引用符が混ざった | `title` `description` の `"` を確認する |
| `BreadcrumbList の item が baseUrl 始まりではありません` | `site.json` の `baseUrl` を変えた直後に古い `dist/` が残っている | `dist/` を消して再ビルド（`node build.mjs --check` が毎回作り直すので、通常は起きない） |
| `<title> がありません` / `meta description がありません` | `title` か `description` が空 | 埋める |
| `search-index.json: リンク切れ` | 記事の URL 生成に失敗 | slug と category を確認する |

**外部リンク（http(s):// のもの）の到達性は `--check` では見ない。** リンク切れは月1の棚卸しで自分で開く（§7）。
